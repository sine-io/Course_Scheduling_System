# 排课流程优化设计

状态：设计与原型完成，生产入口已接入。

日期：2026-08-31

## 设计问题

本项目已经有学期、校历、基础数据、教学任务、规则、自动排课、工作台和发布与输出页面，但用户需要自己记住页面顺序。目标是让教务主任从统一入口完成每次排课，同时仍能在需要时使用完整的独立业务页面。

参考流程来自 [MyZan 排课说明](https://www.myzan.cn/help/index.html)：设置班级、设置课时、科目节数、教师任课、开始排课，再打开课程表调整和输出。本项目不直接复制其灰色按钮和隐式状态，而是把这条记忆路径映射到已有的领域边界。

## 结论

新增一个“排课流程工作台”作为事实性入口，展示当前学期可重复使用的五步流程：

```text
设置班级 → 设置课时 → 科目节数 → 教师任课 → 开始排课
                               ↓
                         课程表调整 → 发布、打印和导出
```

它是业务编排和问题聚合层，不是新的持久化向导，也不保存独立的流程进度。每步状态由已有业务事实实时推导；每个按钮在 `/scheduling/flow` 内挂载现有业务组件或调用已有动作。原有独立业务入口继续保留，并与工作台共用相同数据和接口。

## 五步定义

| 步骤 | 进入条件 | 主动作 | 完成事实 | 权威业务页 |
| --- | --- | --- | --- | --- |
| 设置班级 | 当前学期存在 | 补齐参与排课的班级；按需维护班级作息分配 | 至少有一个可排班级 | `/scheduling/flow?step=classes` |
| 设置课时 | 班级已设置 | 完成作息分组、常规课节次和默认作息 | 作息建议无阻断项，所有班级有可用容量 | `/scheduling/flow?step=periods` |
| 科目节数 | 班级和课时可用 | 为班级录入科目及每周课时；教师可稍后补齐 | 至少有一项课程，课时数量可检查 | `/scheduling/flow?step=subjects` |
| 教师任课 | 科目节数已录入 | 为每项课程指定授课教师 | 每项课程至少有一位教师 | `/scheduling/flow?step=teachers` |
| 开始排课 | 教师任课完整 | 运行前置检查并生成课表草稿 | 求解生成可检查的草稿或明确的未排课时，并记录所用教学任务输入快照 | `/scheduling/flow?step=start` |

生成草稿后进入“课程表调整”，从班级、教师、教室/场地三视角检查、锁定、拖动、局部重排和撤销；发布检查通过后再执行发布、打印和导出。生成后的动作是结果处理，不计入五个准备步骤。

## 内部边界

| 内部概念 | 在短路径中的处理 |
| --- | --- |
| 学期 | 作为当前学期上下文和数据容器，不要求用户先完成一个独立的“学期准备”节点。 |
| 教学任务 | 继续作为教师、班级、科目和每周课时的领域模型；在界面上拆成“科目节数”和“教师任课”两步。 |
| 规则与预排 | 作为开始排课中的前置检查和高级约束；固定课位、合班和特殊场室仍在规则/工作台内维护。 |
| 排课就绪 | 保留现有状态、检查与审计边界；不阻挡用户按五步录入数据，每次点击“开始排课”时复用同一就绪检查与确认，失败仍阻断启动。 |

“预排”是排课前的业务动作，不是新增的持久化状态；固定课位和规则仍由现有课表草稿、规则集版本记录。学期中调课和代课从“发布与输出”之后进入日常运行，不回写工作台步骤状态。

## 状态与推进

工作台只显示四种派生状态：`未开始`、`进行中`、`需处理`、`已完成`。它们不是数据库枚举；每一步的状态来自当前业务事实，不保存向导进度。

```text
设置班级/课时/科目节数/教师任课 ──前置检查──> 开始排课
开始排课 ──生成草稿──> 课程表调整
检查调整 ──发布检查──> 发布与输出
发布与输出 ──发布──> 已发布课表 / 输出
```

规则如下：

- 阻断问题（缺少教师、课时容量超限、无可用作息或硬约束冲突）必须先修复，主动作不可继续。
- 提醒（软规则未满足、仍有少量待排课时）显示影响范围和建议动作；教务主任可以在发布检查中明确确认是否继续，不能静默绕过。
- 导入、规则激活或编辑教学任务会让相关派生阶段重新变为“待处理”，但不会删除已发布课表，也不会偷偷创建草稿。课表通过教学任务输入指纹判断是否仍基于当前任务；指纹只记录生成依据，不保存流程进度。
- 生成失败时保留失败报告和未排课时；用户可回到规则、预排或工作台局部重排，不需要从头开始。
- 工作台的“下一步”只取一个最高优先级动作；“查看全部”才展开次要设置和历史记录。

## 页面信息架构

首屏从上到下固定为：

1. 当前学期和课表草稿/发布状态。
2. 五步流程栏：每步显示状态、数量和可点击入口。
3. “开始排课”主动作面板：标题说明原因，按钮直达自动排课页。
4. 健康度摘要：课程、前置检查、待排课时、冲突和锁定课位。
5. 生成后进入课程表调整，再提供发布、打印和导出。

高级设置默认收起，展开后按来源和规则强度分组。问题详情必须说明“影响对象、数量、建议处理时机”，并提供返回来源页的动作。这样既保留 MyZan 的短路径，也不会把复杂规则藏起来。

## 与 MyZan 的映射

| MyZan | 本项目的映射 | 保留/调整理由 |
| --- | --- | --- |
| 设置班级 | 基础数据中的班级页 | 用现有班级模型承接，不重复创建学期向导 |
| 设置课时 | 作息时间表、校历和作息分组 | 保留容量与免任课概念，显示前置影响 |
| 科目节数 | 教学任务的课时字段 | 先保存“要上什么课”，教师可以稍后补齐 |
| 教师任课 | 教学任务的教师字段、模板导入和来源审计 | 复用标准化导入边界，不让导入激活规则或创建草稿 |
| 开始排课 | 前置检查 + 自动排课 | 规则与预排合并为高级设置，先显示阻断/提醒，再运行求解并保留草稿 |
| 课程表操作 | 课程表调整工作台 | 保留多视角、锁定、撤销、局部重排和暂存区 |
| 打印/导出 | 发布与输出后的显式动作 | 输出不是生成课表的隐式副作用 |
| 临时调课与代课 | 日常运行 | 不改变期初课表草稿或已发布版本 |

不复制以下行为：以按钮灰色作为唯一状态说明、用一个不可解释的总分决定能否排课、删除基础数据时静默级联、或让规则变更直接改动已发布课表。

## 权限与数据边界

工作台面向教务主任和内置系统管理员。教师只看到已发布课表和本人日常事项，不能从工作台编辑教学任务、规则或草稿。发布仍是高风险动作，保留确认、审计和现有发布保护；工作台不新增审批角色。

## 原型评审问题

原型提供三个结构差异明显的方案：

- A「流程指挥台」：先给唯一下一步，适合验证五步工作台流程是否足够清晰。
- B「问题收件箱」：先按阻断程度处理事项，适合验证复杂学校数据的排错效率。
- C「课表画布」：把检查、锁定和局部重排放在主网格，适合验证生成后的连续操作。

评审重点不是选颜色，而是回答：教务主任是否能在五秒内判断现在该做什么；每个阻断项是否能一跳回到来源；在保留提醒的情况下是否敢于发布；以及五步流程是否比现有分散入口更容易复述。

## 验收标准（后续实现）

- 首屏只出现一个主动作，且能说明阻塞原因和影响数量。
- 每个阻断项都有权威页面入口；工作台不创建重复编辑表单。
- 当前草稿固定记录所用规则集版本和教学任务输入指纹；规则或输入变更不会修改已发布课表，并会让自动排课重新成为待处理阶段。
- 自动排课、局部重排、拖动、锁定、撤销和发布检查都能看到结果和审计线索。
- 手机宽度下流程栏可横向查看，按钮和文字不重叠；桌面和移动端均能完整操作。
- 生产实现不新增向导进度字段，不把学期准备改成一次性完成状态。

## 不在本次范围

本设计不实现新的求解算法、规则模板、角色、导入格式、学期中调课与代课模型或发布策略；这些仍沿用现有领域决策和 API。原型只使用内存示范数据，不写入后端。
