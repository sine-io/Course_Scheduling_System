> 研究日期：2026-08-26
> 研究对象：深圳市二一教育科技有限责任公司《二一排课 V10 产品操作手册》（PDF 创建/修改时间 2024-01-10，PDF 共 41 页）
> 下载文件 SHA-256：`04c59b0cbb63521742dab00bca6ebee2c2c6b136741b13f7a40d04f7b782376c`
> 主要来源：[产品手册 PDF](https://paike.21cnjy.com/data/upload/202401/f_d48e8f5e4656b75a03f5bc4723fdf100.pdf)、[二一排课官网首页](https://paike.21cnjy.com/timetable/home.html)、[官网常见问题（FAQ）](https://paike.21cnjy.com/index.php?m=article&f=browse&category=4)。

本文只把 PDF 和厂商官网作为产品事实来源。标记为“观察”的内容是来源明确写出的功能或步骤；标记为“推断/建议”的内容是结合本项目 `CONTEXT.md`、架构规划和 ADR 得出的判断，不应当当成二一排课已经提供的能力。PDF 页码指 PDF 阅读器页码（与手册页脚页码一致）。

## 结论摘要

1. 二一排课的完整主流程是 8 步：**新建排课方案 → 基础数据录入 → 课务安排 → 排课规则定义 → 手工预排 → 自动排课 → 检查调整 → 课表输出**（观察，PDF p.4）。产品宣传页又把它压缩成“设置排课条件 → 自动排课 → 手工调整 → 查询课表 → 打印课表”五个用户动作（观察，PDF p.3；[官网首页](https://paike.21cnjy.com/timetable/home.html)）。这说明复杂配置可以保留在后台，但用户主路径应保持短。
2. 最值得借鉴的不是某个单独规则，而是把每一步都做成**批量输入、网格内编辑、即时校验、可继续优化、就地导出**（推断）。
3. 手册中的“发布”主要是方案列表中的发布/输出动作；没有描述正式审批、版本审计或通知状态机（观察，PDF pp.5、24-29；官网 FAQ 的“课表排好后，如何正式发布？”只说勾选方案后点击“发布课表”）。本项目应借鉴直接、低摩擦的发布入口，但保留现有草稿→检查→确认→发布→审计边界（建议，见 `docs/adr/0009-director-owns-school-business-operations.md`）。
4. 产品把复杂约束分成班级、教师、科目、场地和特殊要求，并允许自动排课后继续优化；本项目可以采用“常用规则先显示、高级规则按需展开”的渐进式界面（推断），而不应一次暴露所有旋钮。

### 流程上的一个重要差异

PDF p.4 明确画出 8 个步骤，而 PDF p.3 的“功能特色”把操作概括为 5 个动作；官网 FAQ 当前也用 5 步（准备基础信息、课程计划、规则、智能排课、发布）。这是同一产品对“内部工作步骤”和“用户记忆路径”的两种表达（观察）。因此，面向本项目用户时可以保留排课前置检查、规则配置等独立业务页面，同时在仪表盘/排课工作台提供一条短路径入口（建议），不必把所有页面合并成一个长向导。

## 2. 关键交互与可简化机制

### 2.1 批量输入与复制

- 科目、教师、年级/班级支持单条、批量和 Excel 导入；课程计划支持批量新增，教学场地和课程计划支持批量导入/追加（观察，PDF pp.7-14）。
- 新学期通过“另存方案”复用上一学期数据；班级升级或改名也建议先另存，避免影响原方案（观察，[FAQ](https://paike.21cnjy.com/index.php?m=article&f=browse&category=4) 的“班级升级”“修改年级名称”条目）。
- 走班/分层设置以勾选班级和科目完成，而不是逐节手排（观察，PDF p.15；[FAQ](https://paike.21cnjy.com/index.php?m=article&f=browse&category=4#section-cat-14)）。

**对本项目的建议（推断/建议）**：保留现有“组合基础数据导入”的预览、冲突分组和事务写入；在教学任务页面增加按年级/科目复制、批量填充周课时/连堂/场地的动作。产品把基础数据跨方案共用，而本项目 `CONTEXT.md` 和架构 D3 采用学期快照，这是有意保护历史数据的设计，不应为了复刻竞品而改成跨学期共享。

### 2.2 约束的渐进式录入

- 产品把约束按对象拆开：班级固排/禁排、教师固排/禁排、科目优先/禁排、场地固排/优先/禁排（观察，PDF pp.17-18）。
- 教师特殊要求继续细分为时间段节数上限、指定节次次数上限、教师互斥、不跨中午、连堂同天、不连天、集中上课（观察，PDF pp.18-21）。
- 科目特殊要求包括科目互斥和顺序限制（观察，PDF p.22）。
- FAQ 的排错路径是“看到提示 → 回到对应设置页检查”：科目属性冲突查科目设置，不同天上课组查课程计划，场地冲突到场地课表找节次，禁排/教师/科目特殊要求分别回到规则页（观察，[FAQ](https://paike.21cnjy.com/index.php?m=article&f=browse&category=4#section-cat-16)）。

**对本项目的建议（推断/建议）**：把常用硬约束（不可排时段、固定课位、教师/班级/场地冲堂）作为默认区，按“教师/班级/科目/场地”分组；将不跨午休、集中上课、科目顺序等高级规则放进可展开面板，并在规则旁显示影响范围和示例。当前项目的排课规则页面主要维护超课时上限，复杂约束已由求解器模型规划但界面仍可逐步补齐；不建议一次性复制 PDF 的所有旋钮。

### 2.3 手工预排与自动排课的衔接

- 产品明确要求在自动排课前先手工设置统一课或固定课（观察，PDF p.4、p.17）。
- 自动排课不是一次性终点：可以选择全校班级或指定科目，完成后做健康度检查，并继续优化不满意结果（观察，PDF p.23）。
- 官网 FAQ 用“课时不平均”“教学进度不一致”“评分低于 80 分”等可理解的结果描述质量问题（观察，[FAQ](https://paike.21cnjy.com/index.php?m=article&f=browse&category=4#section-cat-16)）。FAQ 对评分的解释是“≥80 分代表基本排出且没有冲突/禁排问题；<80 分代表有规则冲突或禁排问题”，这只是厂商定义的产品指标，不能直接视为通用质量标准。

**对本项目的建议（推断/建议）**：继续使用当前工作台的“拖入固定、锁定单元格、冲突检查、自动保存/撤销”交互；自动排课页面应把“全量求解”和“指定科目/局部重排”作为两个清晰入口，并在结果页同时呈现完成率、软约束达成度和未排原因。项目已有前置检查和部分排课/可放宽约束模型，优先改善入口和解释文案，而不是引入一个单一的黑盒分数。

## 3. 冲突处理与调整

### 3.1 产品观察

- 手动拖课时会提示是否违反规则；FAQ 说明红色底色表示禁排规则冲突，黄色底色表示课表存在冲突，并可查看下方规则信息（观察，PDF p.24；[FAQ](https://paike.21cnjy.com/index.php?m=article&f=browse&category=4#section-cat-17)）。
- 场地冲突的建议路径是到“场地课表”定位冲突节次后手动调整；教师冲突可在课表中查看关联教师课表后调整（观察，[FAQ](https://paike.21cnjy.com/index.php?m=article&f=browse&category=4#section-cat-16)）。
- 课表支持锁定整个课表或单节课，锁定课程不会被拖动改变（观察，[FAQ](https://paike.21cnjy.com/index.php?m=article&f=browse&category=4#section-cat-17)）。
- 课表调整历史支持单次撤销/恢复，也可一次性恢复到最初课表；双击课程可打开关联教师课表（观察，[FAQ](https://paike.21cnjy.com/index.php?m=article&f=browse&category=4#section-cat-17)）。

### 3.2 对本项目的建议

1. **冲突反馈要给动作，而不只给颜色。** 在红/黄状态旁显示“冲突对象 + 节次 + 下一步入口”（例如“机房与 2 班同时占用，打开场地视角”）。这是对产品 FAQ 排错路径的提炼（推断），与当前项目 `check-conflict` 后端检查和三视角工作台相容。
2. **保持硬约束不可偷偷违反。** 产品 FAQ 描述了冲突色彩，但手册没有说明哪些冲突允许保存；本项目的硬约束、前置检查和服务端校验应继续作为最终边界（建议），不要为了“黄色可保存”而降低数据正确性。
3. **把局部恢复做成低成本动作。** 产品的调整历史是很直接的撤销/恢复模型；项目可在现有工作台撤销栈、课表版本复制和发布快照之上，补充“恢复到本次自动排课结果/最近发布版本”的明显入口（建议）。

## 4. 发布、通知和日常运行

### 4.1 产品观察

- PDF 的输出章节覆盖单班、教师、场地、全校班级总表、全校教师总表及批量导出打印；导出格式包括 Word 和 Excel，部分总表可横排/竖排、筛选年级，逐班小表可直接调课（观察，PDF pp.24-27）。
- 临时调课可在班级或教师课表中拖动，设置生效时间并保存到临时调课总表；临时代课可从空闲教师、同科目教师或跨科目教师中选择（观察，PDF p.28）。
- 调代课信息查询可生成/打印通知单；还可以按指定节次查询空闲/有课教师（观察，PDF p.29）。
- 官网 FAQ 说明接入“课表助手”微信公众号后可推送调代课通知，教师也可以在公众号申请调代课；移动端课表查询支持微信公众号、网页、钉钉和班牌等方式（观察，[FAQ](https://paike.21cnjy.com/index.php?m=article&f=browse&category=4#section-cat-17)、[FAQ](https://paike.21cnjy.com/index.php?m=article&f=browse&category=4#section-cat-18)）。这属于官网当前服务说明，不代表 2023 年 PDF 的桌面版本身内置这些渠道。
- FAQ 对发布的说明只有“返回首页，勾选要发布的方案，点击左上角发布课表”；未描述审批人、审批状态、通知确认或版本审计（观察，[FAQ](https://paike.21cnjy.com/index.php?m=article&f=browse&category=4)）。

### 4.2 对本项目的建议

- **就地完成输出。** 在版本与发布页或课表查询页提供“当前视角导出”和“批量导出”两个动作，减少用户在查询、打印、发布之间往返（建议）。项目架构已把单张导出与批量/版本级导出分开授权，继续保留这一安全边界。
- **调代课候选前置。** 在受影响节次旁直接显示空闲教师，并按同科优先、当日负载等项目已有规则排序；产品的“空闲/同科/跨科”三类候选是可理解的最小筛选集（观察 + 建议）。
- **通知状态独立于安排生效。** 产品官网有消息推送，但 PDF 没有确认状态。项目已有“站内通知 + 确认收到 + 教务主任确认看板/再次提醒”，应继续保留，不要把教师是否点击通知当成调课生效条件（建议，符合 `CONTEXT.md` 和 ADR-0009）。
- **直接发布但保留保护。** 竞品的单击发布入口可以借鉴；发布前完整性检查、明确确认和审计不能省略（建议，见 `docs/adr/0002-direct-timetable-publication.md`、`docs/adr/0009-director-owns-school-business-operations.md`）。

| 锁定整表/单节、调整历史 | 工作台已有锁定单元格、撤销/重做；版本页支持复制草稿 | **部分对齐。** 可补“恢复到自动排课基线/最近发布版本”快捷动作（建议）。 |
| 输出 Word/Excel、全校总表、逐班调课 | `CONTEXT.md` E1/E2 及版本/查询页面的导出授权 | **方向一致。** 继续把导出放在结果上下文，批量导出只给管理角色（建议）。 |
| 调课生效时间、空闲/同科/跨科代课、通知单 | 项目请假→受影响节次→调课/代课→通知/确认→今日看板流程 | **可直接借鉴。** 项目已有更明确的确认和审计语义；产品的“打印通知单”可作为输出格式补充。 |
| 公众号/钉钉/班牌查询 | 项目以响应式 Web 为 MVP，通知渠道接口可扩展 | **不照搬渠道。** 先保证手机浏览器完成查课表、请假、确认；外部渠道列为适配器。 |

## 6. 建议的最小改进序列（面向流程简化）

以下是从产品观察推导出的实施优先级，不是二一排课官方路线：

1. **工作台入口收敛（低风险）**：在当前仪表盘保留“教学任务 → 自动排课 → 工作台 → 版本与发布”的连续入口；每个入口显示事实性缺项或未排节数，不引入新的跨页面完成状态。
2. **教学任务批量编辑（高收益）**：增加按年级/科目的批量新增、复制上一班配置、连堂/场地批量填充；导入仍先预览、逐行报错、事务提交。
3. **规则分层（高收益）**：默认显示不可排时段、固排/锁定、教师/班级/场地冲堂；“不跨午休、集中上课、科目顺序”等放到高级区，并显示规则影响的任务数量。
4. **自动排课结果闭环（高收益）**：结果页统一提供完成率、软约束达成、未排列表、冲突原因和“仅重排指定科目/局部范围”按钮；允许从诊断直接返回对应数据或规则编辑页。
5. **手动调整保护（低风险）**：保留即时冲突检查；强化关联教师/场地视角跳转、锁定状态和恢复到基线；硬冲突在服务端拒绝写入。
6. **发布与通知（低风险）**：发布前一次完整性检查和确认，发布后生成站内通知；调代课通知继续独立显示确认状态，打印通知单作为可选输出。
7. **移动查询与批量输出（中风险）**：先做响应式 Web 的班级/教师/场地查询和单张导出，再按真实需求增加外部消息适配器；批量/版本导出继续受角色权限控制。

## 7. 不应从竞品倒退的边界

- 不把“评分 ≥80”当成课表可发布的唯一条件；项目的硬约束、完整性检查和发布确认更严格（推断/建议）。
- 不把产品的跨方案共享基础数据复制到历史学期；本项目需要可追溯的学期快照（建议）。
- 不新增独立“排课员”或发布审批流来模拟手册未描述的角色；项目 ADR-0009 已由教务主任直接承担学校业务（建议）。
- 不因产品有排监考模块就把监考并入本轮排课主流程（建议，PDF pp.33-41）。
- 不把微信公众号、钉钉、班牌当成 MVP 前置依赖；项目的响应式 Web 和站内通知先满足核心闭环（建议）。

## 产品声称与独立验证边界

- 官网首页把“AI 算法”“几分钟出课表”“提高排课工作效率 80%”“76000 余所学校需求调研”等作为宣传语；这些是厂商自述，本文不把它们当成性能或市场规模的独立验证（观察，[官网首页](https://paike.21cnjy.com/timetable/home.html)）。
- PDF/FAQ 描述的是界面和操作能力，未提供求解质量基准、冲突算法证明、并发限制或通知送达率。因此本文只据此提炼流程和交互，不据此承诺相同性能（推断/建议）。
- FAQ 页面会随官网更新（当前页面含 2026 年软件版本/截图），与 PDF 的 2023-12 版本可能存在差异；引用 FAQ 时以“官网当前说明”理解，PDF 页码事实仍以手册为准（观察）。
