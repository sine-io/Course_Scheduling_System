# 上手引导、阶段化常用入口与角色权限对齐规格

## Problem Statement

项目已经覆盖学校从学期准备、教学任务、自动/手动排课、课表发布到调课与代课的完整工作流，但第一次接触系统的用户面对的是按功能模块排列的完整菜单，而不是一条明确的工作路径。新排课管理员很难判断哪些功能是首次成功的前置条件、哪些是日常运行功能、哪些只是高级排课或系统运维能力。

项目也已经有四个固定角色和基础 RBAC，但角色定义、页面可见性、动作权限和数据范围需要统一。特别是排课管理员与教务主任不能简单合并；一个人兼任多个角色时，系统需要稳定地解释权限和默认工作视角。当前学期、历史学期、课表草稿、已发布课表和设置向导完成状态也必须有一致的用户含义。

## Solution

建立一套以“首次成功”为中心的角色化信息架构和权限体验：

- 把功能分为 P0 首次成功、P1 日常运行、P2 高级排课、P3 系统运维四个优先级。
- 在完整功能目录上方提供最多五项的“常用”入口，并由角色和当前学期阶段提供默认值。
- 首次发布前引导设置、基础数据、教学任务和排课；首次发布后引导课表查询、今日运行和调课代课。
- 顶部工具栏只承载学校/当前学期、通知、帮助和账号等全局上下文，不承载危险业务动作。
- 保留系统管理员、排课管理员、教务主任、教师四个固定角色；允许用户拥有多个角色，权限取并集，拥有排课管理员角色时默认进入管理视角。
- 将权限落实到查看、编辑、导入、发布、导出、备份、恢复等动作，并明确数据范围；后端授权是最终安全边界。
- 把设置向导完成与首次成功分开。首次成功只在当前正式学期有一张通过完整性检查、没有必排教学任务遗漏并已发布的课表时结束。
- 首次进入明确区分示例数据体验和正式建校；示例数据不能悄悄改变正式学期的引导状态。

## User Stories

1. 作为第一次使用系统的排课管理员，我希望在进入系统时选择示例数据体验或正式建校，以便不用把学习操作和正式数据录入混在一起。
2. 作为第一次使用系统的排课管理员，我希望看到一条按顺序排列的首次成功路径，以便知道接下来应配置什么。
3. 作为第一次使用系统的排课管理员，我希望设置向导在中断后保留当前步骤，以便从上次停止的位置继续。
4. 作为第一次使用系统的排课管理员，我希望知道设置向导完成不等于课表已经完成，以便不会过早认为系统已经可以投入使用。
5. 作为第一次使用系统的排课管理员，我希望仪表盘显示当前 P0 待办和唯一的下一步动作，以便不必在完整菜单中寻找入口。
6. 作为第一次使用系统的排课管理员，我希望系统明确指出学期、作息、校历、基础数据、教学任务和完整性检查中哪一项阻塞了排课，以便按问题顺序处理。
7. 作为第一次使用系统的排课管理员，我希望示例数据路线能运行一次自动排课并查看发布结果，以便在录入正式数据前理解完整流程。
8. 作为第一次使用系统的排课管理员，我希望正式路线直到第一张正式课表发布前都保留新手待办，以便“导入数据”不会被误认为首次成功。
9. 作为排课管理员，我希望首次发布前的常用入口依次包含当前待办、教学任务、自动排课、排课工作台和版本与发布，以便按 P0 主流程工作。
10. 作为排课管理员，我希望首次发布后的常用入口转为仪表盘、课表查询、今日看板、调课与代课和版本与发布，以便快速进入日常运行。
11. 作为排课管理员，我希望可以固定、排序、恢复默认常用入口，以便在不丢失系统推荐的前提下适应个人工作习惯。
12. 作为排课管理员，我希望最近访问只在常用入口有空位时补充，而不是覆盖阶段推荐，以便偶然打开的高级页面不会干扰主流程。
13. 作为排课管理员，我希望只能在当前学期进行常规写入和发布，以便不会误修改历史学期。
14. 作为排课管理员，我希望可以切换当前学期并清楚看到当前上下文，以便多个学期并存时不会把数据写入错误学期。
15. 作为排课管理员，我希望发布课表前看到完整性检查结果和明确确认，以便生成草稿与正式发布保持清晰区别。
16. 作为排课管理员，我希望发布、删除、备份恢复和权限变更留下审计记录，以便高风险操作可追溯。
17. 作为教务主任，我希望在首页看到全校运行摘要、课表查询、今日看板、版本监督和代课统计，以便履行监督职责。
18. 作为教务主任，我希望能查看排课草稿但不能编辑草稿或发布课表，以便监督不会变成未经授权的排课操作。
19. 作为教务主任，我希望可以维护校历、登记或处理全校请假、处理调课与代课和发送运行提醒，以便完成有限的日常教务工作。
20. 作为教务主任，我希望不能修改教学任务、排课草稿或发布课表，以便排课执行责任仍归排课管理员。
21. 作为教师，我希望首页只提供课表查询、请假登记、通知和我的代课课时，以便不被基础数据和排课工具干扰。
22. 作为教师，我希望能查看已发布的全校课表，以便了解班级、教师和教室安排。
23. 作为教师，我希望只能修改自己的请假、确认自己的通知并查看自己的统计，以便保护其他教师和学校排课数据。
24. 作为教师，我希望看不到排课草稿，以便不会把尚未确认的安排当成正式课表。
25. 作为系统管理员，我希望能管理账号、角色、备份恢复和系统设置，以便负责系统安全而不必承担日常排课操作。
26. 作为系统管理员，我希望能查看全部业务数据，以便在故障排查和恢复时拥有完整上下文。
27. 作为一个同时拥有排课管理员和教师角色的用户，我希望权限取两个角色的并集，以便兼任职责不需要重复登录。
28. 作为一个同时拥有排课管理员和教师角色的用户，我希望默认进入排课管理视角，同时仍能完成本人请假和通知确认，以便管理工作和个人事务都可达。
29. 作为一个同时拥有排课管理员和教务主任角色的用户，我希望系统保留两个责任身份而不合并角色，以便审计能区分执行排课与监督排课。
30. 作为任何登录用户，我希望顶部工具栏显示学校和当前学期、通知、帮助和账号，以便获得全局上下文而不被高风险按钮干扰。
31. 作为任何登录用户，我希望完整功能目录仍然可访问，以便常用入口不会限制系统能力。
32. 作为管理角色，我希望历史或归档学期可以查询和复制但默认只读，以便复用历史数据而不误发布。
33. 作为开发或维护人员，我希望权限规则在后端动作边界统一执行，以便隐藏前端菜单不能被绕过成为安全漏洞。
34. 作为维护人员，我希望项目不引入自定义角色编辑器、发布审批流或复杂组织权限，直到有真实学校需求，以便第一阶段保持可理解和可审计。

## Implementation Decisions

- 功能优先级固定为：P0 首次成功（设置向导、学期与作息、校历、基础数据、教学任务、自动/手动排课、完整性检查、版本发布、课表查询）；P1 日常运行（请假、调课与代课、今日看板、通知、记录、课时统计、常用导出）；P2 高级排课（多草稿、混合学制、走班、协同教学、连堂、复杂约束、部分排课、无解定位）；P3 系统运维（账号权限、学校设置、备份恢复、审计、SMTP、升级和健康检查）。
- 导航由全局工具栏、常用入口和完整功能目录组成。常用入口最多五项，按角色默认值、首次成功阶段化推荐、用户固定/排序、最近访问补位的顺序决定。
- 首次发布前的排课管理员默认入口为：当前待办、教学任务、自动排课、排课工作台、版本与发布。首次发布后为：仪表盘、课表查询、今日看板、调课与代课、版本与发布。
- 教务主任默认入口为：仪表盘、课表查询、今日看板、版本与发布、代课课时统计。教师默认入口为：课表查询、请假登记、通知、我的代课课时。系统管理员默认入口为：仪表盘、系统管理、备份恢复、账号权限、上手指南（首次发布后以课表查询替换上手指南）。
- 顶部工具栏只承载学校、当前学期、通知、帮助和账号等全局上下文。发布、删除、备份恢复和权限变更不能成为一键执行的顶部动作。
- 保留四个固定角色：系统管理员、排课管理员、教务主任、教师。角色是工作责任集合，不是组织层级；排课管理员和教务主任不合并，不自动继承。
- 一个用户可以拥有多个角色；权限取并集；只要拥有排课管理员角色，默认进入管理视角，不提供改变授权结果的角色切换器。
- 权限必须至少区分查看已发布课表、查看草稿、编辑基础数据、编辑教学任务/排课草稿、运行自动排课、发布、维护校历、登记/处理全校请假、处理调课与代课、本人事务、单张导出、批量/版本导出、备份恢复、账号和角色管理。
- 系统管理员拥有全部系统和业务权限；排课管理员拥有核心教学任务、排课和发布写权限；教务主任拥有全校查看权限及校历、请假、调课与代课等有限运行写权限，但不能编辑核心排课或发布；教师只写本人事务并使用已发布课表。
- 系统管理员和排课管理员可以编辑课表草稿；教务主任可以查看草稿但不能编辑；教师不可见草稿。单张已发布课表可由登录用户导出，批量或版本级导出限管理角色。
- 只有系统管理员或排课管理员可以切换当前学期；历史/归档学期默认只读，可查询和复制，不能常规写入或发布。
- 设置向导完成状态与首次成功状态分离。首次成功状态应由正式学期、完整性检查、必排教学任务无遗漏和已发布课表这些权威业务状态推导，避免引入可被误更新的重复完成标记。
- 示例数据体验和正式建校是两条明确的首次入口；示例数据不能改变正式学期的首次成功状态。
- 排课管理员直接发布课表，教务主任查看和监督；第一阶段不引入发布审批流。发布仍需完整性检查、确认和审计。
- 前端按角色和阶段隐藏不相关入口，但后端 HTTP 授权边界是最终安全边界；所有动作和数据范围都必须在后端再次校验。
- 优先复用现有的认证、路由守卫、设置向导、仪表盘、学期生命周期、版本发布和 `require_roles` 授权接口；只有现有接口无法表达首次成功、当前学期或用户入口偏好时，才增加最小的读模型或偏好接口。
- 常用入口的固定/排序偏好按用户保存，不改变权限；恢复默认后重新使用角色和阶段默认值。偏好缺失时必须有稳定默认顺序。
- 界面需在桌面、平板和手机上保持可用；键盘用户可以访问常用入口、当前学期选择、待办和所有高风险确认。

## Testing Decisions

- 测试只验证外部行为：用户看到的入口、可执行的动作、状态转换、拒绝结果和数据范围，不测试导航数组、组件内部状态或具体实现函数。
- 主要测试接口是浏览器端的角色/生命周期用户旅程：从全新系统选择示例或正式路线，完成向导、P0 待办、首次发布，以及发布后的阶段化入口切换。
- 安全测试接口是后端 HTTP 授权边界：使用四种角色、兼任角色、当前/历史学期、草稿/已发布课表和本人/全校数据，验证允许和拒绝的实际响应。
- 排课管理员场景应覆盖：首次发布前五项常用入口、数据阻塞提示、自动排课、草稿查看、完整性检查、发布确认、首次成功结束和发布后的常用入口。
- 教务主任场景应覆盖：全校查看、草稿只读、校历维护、全校请假、调课与代课处理、统计和导出边界，以及发布/核心排课编辑被拒绝。
- 教师场景应覆盖：已发布全校课表查询、本人请假、本人通知确认、本人统计，以及草稿、他人请假、教学任务和排课接口被拒绝。
- 多角色场景应覆盖：权限并集、默认管理视角、仍可执行本人事务、无角色切换导致的授权变化。
- 学期场景应覆盖：切换当前学期、历史/归档只读、禁止误发布、复制历史数据和明确的当前上下文。
- 高风险动作应覆盖：发布前确认、删除/恢复/权限变更的授权和审计，且常用入口不能绕过保护。
- 响应式和无障碍回归应验证：窄屏常用入口可达、键盘操作、焦点顺序、状态消息和没有横向溢出。
- 复用项目已有的设置向导、完整旅程、应用壳层、教师账号、系统设置、认证、向导、发布和备份测试模式；新增断言应针对用户可观察结果。

## Out of Scope

- 自定义角色和任意权限编辑器。
- 发布审批流、主任审批后才能发布的状态机。
- 按校区、年级、部门或组织树的复杂数据范围模型。
- 完全自由的菜单布局编辑器。
- 让发布、删除、备份恢复或权限变更成为无确认的一键动作。
- 企业微信、钉钉等外部通知平台适配。
- 重新设计排课求解器、教学任务模型或课表网格的核心算法。
- 将示例数据直接转化为正式学期数据。

## Further Notes

- 项目当前已经有四角色 RBAC、设置向导、仪表盘快捷入口和教师“常用”导航；本规格要求把这些现有能力统一到同一套领域规则，而不是另起一套权限系统。
- 已接受的架构背景记录在角色驱动导航、排课管理员直接发布课表、首次成功与当前学期上下文三个 ADR 中；实现时不得悄悄引入角色合并或发布审批。
- 规格对应的领域词汇记录在根目录 `CONTEXT.md`。若实现过程中发现“首次成功”“当前学期”“草稿可见范围”无法由现有权威数据推导，应先更新 ADR 和规格，再扩展状态模型。
