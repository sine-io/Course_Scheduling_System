# 学期准备、角色权限与直接功能导航规格

> 导航部分以 [ADR-0005](../adr/0005-dashboard-shortcuts-and-unified-operations-views.md) 为准，学期准备以 [ADR-0010](../adr/0010-distributed-semester-preparation.md) 为准，角色权限以 [ADR-0009](../adr/0009-director-owns-school-business-operations.md) 为准。

## Problem Statement

项目已经覆盖学校从学期准备、教学任务、自动/手动排课、课表发布到调课与代课的完整工作流。第一次接触系统的管理用户需要先建立学制、学期、作息和基础数据，再进入正常业务页面。

项目使用三种固定职责和基础 RBAC，但角色定义、页面可见性、动作权限和数据范围需要统一。学校没有独立排课员，教务主任承担全部学校业务；内置系统管理员独占系统级管理；教师只使用已发布课表和本人事务。当前学期、历史学期、课表草稿和已发布课表必须有一致的用户含义，不能再引入一套跨页面准备状态。

## Solution

建立一套以真实业务页面为初始入口的角色化信息架构和权限体验：

- 把功能分为 P0 建校与排课、P1 日常运行、P2 高级排课、P3 系统运维四个优先级。
- 在仪表盘提供每个角色最多三个固定“快捷入口”，不保存个人固定或最近访问偏好。
- 侧边栏直接按学期准备、排课主流程、日常运行、报表和系统管理五组展示获准页面，不增加“完整功能”包装层。
- 全新管理用户从“学期与作息时间表”开始，再分别进入基础数据、作息分组和校历页面；不提供路线选择或内置示例学校数据。
- 顶部工具栏只承载学校/当前学期、通知、帮助和账号等全局上下文，不承载危险业务动作。
- 只保留内置系统管理员、教务主任和教师三种固定职责；普通账号可兼任教务主任和教师，权限取并集，拥有教务主任角色时默认进入管理视角。
- 将权限落实到查看、编辑、导入、发布、导出、备份、恢复等动作，并明确数据范围；后端授权是最终安全边界。
- 各准备页面只保存其所属业务数据；仪表盘显示中性摘要，排课前置检查继续作为排课领域的独立业务概念。

## User Stories

1. 作为第一次使用系统的教务主任，我希望进入后直接看到学期页面，以便立即开始建立学校数据。
2. 作为第一次使用系统的教务主任，我希望系统不提供另一条内置示例路线，以便所有学期都表示学校实际工作数据。
3. 作为第一次使用系统的教务主任，我希望能在学期、基础数据、作息分组和校历页面之间自由往返，以便中断后从实际缺项继续。
4. 作为教务主任，我希望仪表盘把事实性提醒链接到对应页面，以便不必寻找跨页面的完成清单。
5. 作为教务主任，我希望排课前置检查明确区分阻断项与建议项，以便知道何时可以开始排课。
6. 作为教务主任，我希望无学期时能从仪表盘空状态进入学期页面，以便侧栏无需长期占用入口。
7. 作为维护人员，我希望旧的向导路由、接口和状态不会重新出现在运行时，以便删除的能力不会继续形成兼容负担。
8. 作为教务主任，我希望 Excel 模板保留示范行，以便理解字段格式但不会自动写入整套学校数据。
9. 作为教务主任，我希望仪表盘固定提供排课工作台、教学任务和今日看板快捷入口，以便快速回到主流程。
10. 作为教师，我希望仪表盘固定提供课表查询、请假登记和通知快捷入口，以便快速处理本人事务。
11. 作为任何角色，我希望侧边栏在五个固定功能分组中直接展示获准页面，以便无需展开额外目录层级。
12. 作为维护人员，我希望侧栏不保存个人排序或最近访问状态，以便导航状态不会成为另一套权限来源。
13. 作为教务主任，我希望只能在当前学期进行常规写入和发布，以便不会误修改历史学期。
14. 作为教务主任，我希望可以切换当前学期并清楚看到当前上下文，以便多个学期并存时不会把数据写入错误学期。
15. 作为教务主任，我希望发布课表前看到完整性检查结果和明确确认，以便生成草稿与正式发布保持清晰区别。
16. 作为教务主任，我希望课表发布留下审计记录，以便学校正式安排的变更可追溯。
17. 作为教务主任，我希望在首页看到全校运行摘要、排课进度、今日看板、版本和代课统计，以便履行全部教务职责。
18. 作为教务主任，我希望能查看和编辑排课草稿并发布课表，以便不需要另设排课员账号。
19. 作为教务主任，我希望可以维护校历、登记或处理全校请假、处理调课与代课和发送运行提醒，以便完成日常教务工作。
20. 作为教务主任，我希望看不到账号权限、学校与 SMTP 设置、备份恢复、全局审计和永久删除，以便系统级职责仍由内置管理员承担。
21. 作为教师，我希望首页只提供课表查询、请假登记、通知和我的代课课时，以便不被基础数据和排课工具干扰。
22. 作为教师，我希望能查看已发布的全校课表，以便了解班级、教师和教室安排。
23. 作为教师，我希望只能修改自己的请假、确认自己的通知并查看自己的统计，以便保护其他教师和学校排课数据。
24. 作为教师，我希望看不到排课草稿，以便不会把尚未确认的安排当成正式课表。
25. 作为系统管理员，我希望能管理账号、角色、备份恢复和系统设置，以便负责系统安全而不必承担日常排课操作。
26. 作为系统管理员，我希望能查看全部业务数据，以便在故障排查和恢复时拥有完整上下文。
27. 作为一个同时拥有教务主任和教师角色的用户，我希望权限取两个角色的并集，以便兼任职责不需要重复登录。
28. 作为一个同时拥有教务主任和教师角色的用户，我希望默认进入排课管理视角，同时仍能完成本人请假和通知确认，以便管理工作和个人事务都可达。
29. 作为学校管理者，我希望系统不强制只能存在一个教务主任账号，以便未来组织安排变化时无需修改权限模型。
30. 作为任何登录用户，我希望顶部工具栏显示学校和当前学期、通知、帮助和账号，以便获得全局上下文而不被高风险按钮干扰。
31. 作为任何登录用户，我希望通知页面按权限提供“我的通知”和“确认看板”视图，以便消息阅读和确认追踪在同一工作面完成。
32. 作为管理角色，我希望历史或归档学期可以查询和复制但默认只读，以便复用历史数据而不误发布。
33. 作为开发或维护人员，我希望权限规则在后端动作边界统一执行，以便隐藏前端菜单不能被绕过成为安全漏洞。
34. 作为维护人员，我希望项目不引入自定义角色编辑器、发布审批流或复杂组织权限，直到有真实学校需求，以便第一阶段保持可理解和可审计。

## Implementation Decisions

- 功能优先级固定为：P0 建校与排课（学期与作息、校历、基础数据、教学任务、自动/手动排课、排课前置检查、版本发布、课表查询）；P1 日常运行（请假、调课与代课、今日看板、通知、记录、课时统计、常用导出）；P2 高级排课（多草稿、混合学制、走班、协同教学、连堂、复杂约束、部分排课、无解定位）；P3 系统运维（账号权限、学校设置、备份恢复、审计、SMTP、升级和健康检查）。
- 导航由全局工具栏、仪表盘快捷入口和五个侧栏功能分组组成；仪表盘属于学期准备；快捷入口最多三项，由角色职责固定决定，不接受个人排序或最近访问补位。
- 教务主任和内置系统管理员默认快捷入口为：排课工作台、教学任务、今日看板。教师默认入口为：课表查询、请假登记、通知。
- 系统管理分为系统管理、备份恢复和账号权限三个独立页面；通知和通知确认看板合并为同一页面的两个权限视图。
- 顶部工具栏只承载学校、当前学期、通知、帮助和账号等全局上下文。发布、删除、备份恢复和权限变更不能成为一键执行的顶部动作。
- 只保留三种固定职责：唯一内置系统管理员、教务主任和教师；删除独立排课员角色，不提供兼容层。
- 一个用户可以拥有多个角色；权限取并集；只要拥有教务主任角色，默认进入管理视角，不提供改变授权结果的角色切换器。
- 权限必须至少区分查看已发布课表、查看草稿、编辑基础数据、编辑教学任务/排课草稿、运行自动排课、发布、维护校历、登记/处理全校请假、处理调课与代课、本人事务、单张导出、批量/版本导出、备份恢复、账号和角色管理。
- 内置系统管理员拥有全部系统和业务权限；教务主任拥有除管理员专属功能外的全部学校业务权限；教师只写本人事务并使用已发布课表。
- 内置系统管理员和教务主任可以编辑课表草稿、运行排课、发布并执行批量或版本级导出；教师不可见草稿，只能查询和单张导出已发布课表。
- 只有系统管理员或教务主任可以切换当前学期；历史/归档学期默认只读，可查询和复制，不能常规写入或发布。
- 学期、基础数据、作息分组和校历是各自的初始设置入口；无学期时仪表盘直接链接学期页面，不保存跨页面步骤、完成状态或新手路线。
- 仪表盘的数量和提醒必须由当前学期真实数据推导；排课前置检查和排课准备确认由排课页面维护，不复制到准备页面。
- 教务主任直接发布课表；第一阶段不引入发布审批流。发布仍需完整性检查、确认和审计。
- 前端按角色和数据可用性隐藏不相关入口，但后端 HTTP 授权边界是最终安全边界；所有动作和数据范围都必须在后端再次校验。
- 优先复用现有的认证、路由守卫、仪表盘、学期生命周期、版本发布和 `require_roles` 授权接口；导航不再增加用户偏好读写模型。
- 界面需在桌面、平板和手机上保持可用；键盘用户可以访问快捷入口、当前学期选择和所有高风险确认。

## Testing Decisions

- 测试只验证外部行为：用户看到的入口、可执行的动作、状态转换、拒绝结果和数据范围，不测试导航数组、组件内部状态或具体实现函数。
- 主要测试接口是浏览器端的角色/生命周期用户旅程：全新系统创建学期并完成分散的准备页面，再完成排课和发布。
- 安全测试接口是后端 HTTP 授权边界：使用三种职责、兼任角色、当前/历史学期、草稿/已发布课表和本人/全校数据，验证允许和拒绝的实际响应。
- 教务主任场景应覆盖：学期与基础数据页面、按事实提醒跳转、角色固定快捷入口、直接功能分组、自动排课、草稿查看、完整性检查和发布确认。
- 内置系统管理员场景应覆盖：账号与角色、教师账号绑定、学校与 SMTP 设置、备份恢复、全局审计、永久删除和管理员恢复。
- 教师场景应覆盖：已发布全校课表查询、本人请假、本人通知确认、本人统计，以及草稿、他人请假、教学任务和排课接口被拒绝。
- 多角色场景应覆盖：权限并集、默认管理视角、仍可执行本人事务、无角色切换导致的授权变化。
- 学期场景应覆盖：切换当前学期、历史/归档只读、禁止误发布、复制历史数据和明确的当前上下文。
- 高风险动作应覆盖：发布前确认、删除/恢复/权限变更的授权和审计，且快捷入口不能绕过保护。
- 响应式和无障碍回归应验证：窄屏侧栏分组和快捷入口可达、键盘操作、焦点顺序、状态消息和没有横向溢出。
- 复用项目已有的学期、基础数据、应用壳层、教师账号、系统设置、认证、发布和备份测试模式；新增断言应针对用户可观察结果。

## Out of Scope

- 自定义角色和任意权限编辑器。
- 发布审批流、主任审批后才能发布的状态机。
- 按校区、年级、部门或组织树的复杂数据范围模型。
- 完全自由的菜单布局编辑器。
- 让发布、删除、备份恢复或权限变更成为无确认的一键动作。
- 企业微信、钉钉等外部通知平台适配。
- 重新设计排课求解器、教学任务模型或课表网格的核心算法。

## Further Notes

- 项目当前使用三种固定职责、分散的学期准备页面和仪表盘快捷入口；固定快捷入口与通知视图以 ADR-0005 为准，角色权限以 ADR-0009 为准，学期准备以 ADR-0010 为准。
- 已接受的架构背景记录在仪表盘快捷入口、教务主任承担全部学校业务、当前学期上下文和分散学期准备 ADR 中；实现时不得重新引入独立排课员、跨页面准备状态或发布审批。
- 规格对应的领域词汇记录在根目录 `CONTEXT.md`。若实现过程中发现“当前学期”“草稿可见范围”或排课前置检查无法由现有权威数据表达，应先更新 ADR 和规格，再扩展状态模型。
